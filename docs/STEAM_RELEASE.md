## 二、本轮完成的技术改造（可直接验收）

### 2.0 ⛔ 最高优先级：CI 一直是坏的，线上部署静默停摆了 4 个提交

**这是本轮最重要的发现，而且它一直在骗你。**

**现象**：GitHub Pages 上跑的不是最新代码。
7fcf835 之后连续三次部署全部失败，页面一直停在那次成功的构建上 ——
也就是说线上演示站缺了之后**三轮**的全部缺陷修复（K-1 ~ K-8、贬官失效、读档丢事件等）。
你在线上看到的"看不到幽灵模式"，根源就在这里，不是设置问题。

**根因**（gh run view --log-failed 里的真实报错）：

`
TypeError: webidl.util.markAsUncloneable is not a function
❯ new CacheStorage node_modules/undici/lib/web/cache/cachestorage.js:20:17
❯ Object.<anonymous> node_modules/jsdom/lib/api.js:12:33
`

链条是 jsdom@30 → undici@8.11.2，后者的
lib/web/webidl/index.js 里有一行：

`js
const { markAsUncloneable } = require('node:worker_threads')
webidl.util.markAsUncloneable = markAsUncloneable
`

markAsUncloneable 自 **Node 22.19** 才存在于 
ode:worker_threads。
CI 当时跑的是 **Node 20**，它是 undefined，
于是 undici/index.js 顶层的 
ew CacheStorage() 当场抛错，
整步单元测试失败 → 部署被拦下。

**为什么本地看不出来**：开发机是 Node 26，
equire('node:worker_threads').markAsUncloneable
存在，所以本地 46 个用例全绿。**这是一个只有 CI 才会暴露的缺陷。**

**修复**：
- CI Node 版本 20 → 24，并把 package.json 的 engines.node 提到 >=22.22.2
  （这个下限是 scripts/check-node-engine.cjs 扫 
ode_modules 里所有
  engines.node 取最大值得到的真实要求，不是猜的）
- 新增 scripts/check-node-engine.cjs 作为 CI 的**第一步**：Node 版本一退回，
  立刻在该步骤报清楚原因，而不是让��在 200 行 vitest 输出里找 TypeError

### 2.5 排版与版面：把"字体太小 / 布局不紧凑"量化后修掉

这两条反馈我先在真实 Chromium 里量了基线，再改：

| 项 | 之前 | 之后 | 怎么量的 |
| --- | --- | --- | --- |
| 事件正文 `.narrative-paragraph` | **12.8px** | **17.1px** | `getComputedStyle` |
| 选项标题 `.choice-title` | 13.6px | 17.6px | 同上 |
| 选项描述 `.choice-description` | 12.0px | 15.8px | 同上 |
| 引语 / 情境提示 | 12.8px | 16.2px | 同上 |
| 侧栏辅助标签 | 低至 9.9px | ≥12.6px | 同上 |
| 1440×900 页面底部空档 | **183px** | **20px**（即页面内边距） | 取最深子元素的 `bottom` |

**排版怎么改的**：全局 UI 都用 `rem` 排版，所以 `html { font-size }`
就是唯一的排版旋钮 —— 16px → **18px**（+12.5%），
再把阅读关键的那几条（正文 / 选项 / 引语 / 提示）各上调一档。
改这一个值会同时放大 `rem` 间距，所以**改完必须跑布局回归**（也确实跑出了回归，见下）。

**版面怎么改的**：把 `.game-screen → .game-screen-body → .game-main
→ .main-content → .event-display` 这条链改成纵向 flex 骨架，
各层依次 `flex: 1`，事件区与侧栏各自内部滚动。
宽屏（>1024px）额外用 `height: 100dvh` 把可视高度锁定。

> **只写 `min-height` 是不够的**：那样容器高度仍由内容决定，
> 子项的 `flex: 1` 只是在一个"已经被内容撑大"的高度里分份额，起不到压缩作用。
> 这也是为什么必须实测而不能靠推理。

**这一步踩到一个坑，值得记下来**：改完第一版，`layout.mjs` 立刻报
`laptop-1280`（1280×800，Steam Deck 分辨率）底部操作栏被顶出视口 224px。
原因是两侧栏面板加起来约 880px，而 `align-items: stretch` 让栅格行高被**侧栏内容**决定，
于是这一行高于可用高度，把操作栏挤了出去。
补上侧栏的 `min-height: 0` + `overflow-y: auto`，并给 `.game-main` 加 `overflow: hidden` 才修好。

> 顺带补强了回归网：`tests/layout.mjs` 原来**只测标题屏**。
> 现在会对 9 档视口**逐档进游戏**再查一遍（横向溢出 / 操作栏可见性 / 事件面板高度），
> 因为上面这类 flex 骨架的 bug 只在真实内容下才暴露。
> 同时因为字号放大了 12.5%，标题屏的高度断点也必须跟着调 ——
> 否则 iPhone 14 竖屏（390×844）会因为"刚好落在断点缝隙里"而把主按钮顶到折叠线以下。

| 测量项 | 结果 |
| --- | --- |
| 运行时帧间隔（连续推进 30 回合） | P50 **16.7ms** / P99 **16.8ms**，超过 32ms 的帧 **0 个** |
| 长任务（>50ms） | 全程 1 个，57ms |
| 冷启动 FCP（本地） | 112–132ms |
| 冷启动（线上 GitHub Pages） | FCP 1.34s，54 个请求 / 1.36MB |

也就是说**运行时并不卡**（16.7ms 正是 60fps 的理论间隔）。
你感受到的"卡"更可能来自两处：

1. **线上跑的是 4 个提交之前的旧代码**（见 2.0）。旧代码里有真实的主线程热点。
2. **首屏 54 个请求**：其中 46 个是 JS 分片。Vite 把 17 个历史年份 + 18 个过渡年份
   各自分包，而 `src/data/events/index.ts` 静态 import 全部，于是首屏一次性预取 1.36MB。

**本轮做的引擎侧优化**（真实缺陷，只是不会被单测自动发现）：

- `ALL_EVENTS` 提到模块级构建一次。此前 4 个函数体内各写了一遍
  `[...initialEvents, ...allGrayChoiceEvents]`，每次调用新建一个约 2000 项的数组并逐个拷贝，
  而这几个函数是**每月推进都会跑**的热路径，一局下来是数千次无谓的 2000 元素数组分配。
- `pickEvent` 的 4 处 `eventHistory.includes(e.id)` 改为 `Set.has`。
  `eventHistory` 一局能涨到 200+ 项、候选常上千项，原来是 O(n×m) 的字符串比较 ——
  而且**越到后期越卡**。
- `findAllEventsForState` 的 `history.lastIndexOf()` 改为一张 `Map` 索引表，
  它在 `withCooldown` 里对每个可重复事件各扫一遍，是该函数最大的热点。

> 改 `pickEvent` 时踩了个坑，编译器帮我抓住了：我最初把"最近 5 条"
> 也换成了"全部已见"，那会**永久耗尽支线事件**（情感线 / 权色线本就该反复遇到）。
> `noUnusedLocals` 报出 `recent` 未使用才暴露出来，已改回原语义。

**没做的与原因**：首屏 46 个 JS 分片没有改成按年份懒加载。
那需要把同步的事件挑选改成异步，会大幅改动引擎核心，风险明显高于收益；
而桌面版（Steam 实际发行形态）跑在本地磁盘上，这个成本根本不存在。
如果将来要优化，更划算的方向是先合并年份分片数量，而不是改引擎。

> **后续（第六轮）**：上面那句建议已经落地 —— `vite.config.js` 改成
> 历史 4 年一片 / 过渡 5 年一片，产物 JS 分片 **46 → 23**，总体积不变，
> 省掉的是 23 次请求往返。全量预取本身仍在（`events/index.ts` 是静态 import），
> 详见 [KNOWN_ISSUES.md](KNOWN_ISSUES.md) 第一节 1.1 与第六轮清单。

### 3.5 ✅ 成就数量已压到 Steam 上限以内（并修掉一个真实缺陷）

**这里原本是两个问题叠在一起，而且其中一个是真缺陷。**

#### （1）真实缺陷：5 个结局成就从未登记到 Steam

上一轮修「34 个结局里有 5 个没有对应成就」时，5 个成就只补进了
`src/types/achievement.ts`，**漏了 `desktop/steam.cjs` 的映射表**。
后果：这 5 个成就永远不会同步到 Steam，结局图鉴在 Steam 侧永远缺 5 个勾。

它之所以一直没被发现，是因为当时的断言是这样的：

```js
check('映射表条数 = 内部成就数', apiNames.length, steam.INTERNAL_ACHIEVEMENT_COUNT)
```

**比对的是两个手写常量**（都是 105）—— 它们完全可能一起漂移。
真实的源码条数其实是 **110**。

已改为**直接解析 `src/types/achievement.ts`** 与映射表逐条对拍
（`desktop/smoke-test.cjs` §6b），三种漂移都会失败：

- 游戏内有、映射表缺的（会永远不同步）
- 映射表有、游戏内已删的（会注册一个不存在的成就）
- 手写常量与源码实际条数不一致

这个新断言在加上去的第一次运行就抓出了上面那个缺陷。

#### （2）成就数超限：110 → 100

Steam 对单个 app 的成就数量有上限（公开规则为 100 个；建议在 Steamworks
后台文档再确认一次）。而且 **API Name 一经创建就无法修改、只能删除重建**，
所以"先全建上去再说"这条路走不通，必须在建之前就定。

已裁掉 10 个（每处的理由都写在 `achievement.ts` 里）：

| 删除的 id | 理由 |
| --- | --- |
| `master_collector`、`ultimate_master` | 收集链的中间档。**它们对玩家本来就不可见**：`getUnlockedAchievements()` 按 `group` 分桶、每桶只展示 `priority` 最高的已解锁项，中间档只贡献"多一个勾"的观感 |
| `ending_collection_15` | 同理，`collection` 组（5/15/30）的中间档 |
| `wealthy`、`scholar`、`administrator`、`military_genius`、`popular` | 属性阈值 80 档，与各自的 95 档同属一个 `group`，同样因分桶而不可见 |
| `first_choice`（100 个事件都选第一个选项）、`saver`（存档 30 次） | 纯"操作频次"统计型成就，衡量点击习惯而非游戏体验，认真玩的人反而拿不到 |

保留了 `random_player` 与 `careful_player`：它们分别有真实入口
（「听天由命」按钮 / 回退功能），描述的是玩法而非机械操作。

**旧存档兼容**：删掉成就会带来一个容易漏的问题 —— 老存档里仍然留着这些 id。
不清掉的话"已解锁 N 个"的计数会虚高，而 `collector`(30) 与 `legendary_master`(全部)
的判据都依赖这个计数，玩家会莫名提前拿到"成就收藏家"、甚至白拿"传奇大师"。
因此在 `cloneAchievementData`（所有读写边界的唯一入口）统一剔除，
并由 `tests/unit/achievement.steamLimit.test.ts` 钉住。

**现在的状态**：`npm run check:steam` 全绿 —— 100 个成就 = 100 条映射，
不超过上限，与源码逐条一致。该检查已加入 CI。

> 后续增删游戏内成就时，记得同步改 `desktop/steam.cjs` 并跑 `npm run check:steam`。

1. **决定 §3.1 的内容方案** —— 这一步决定整个项目能不能上 Steam，其他都是次要的
2. **确认 §3.2 的素材授权** —— 尤其是 BGM，这是最容易在发行后被投诉的地方
3. 在 Windows 上跑通 `npm run desktop:dist`，实机验收桌面版
4. 注册 Steamworks 账号，拿到 AppID
5. 按 `desktop/steam/DEPOT_CHECKLIST.md` 配置后台与成就（现在是 100 个，可全量创建）
6. 用 `tests/store-assets.mjs` 产出物料上传；请美术重做封面与截图
7. 提交审核（Valve 通常需要 5 个工作日以上，首次可能更久）

> 第 1 步没解决之前，第 3–7 步的投入都有归零的风险。
>
> 另外建议顺手做一件事：**给 Pages 部署失败配一个通知**。
> 本轮发现的 CI 静默停摆正是"部署失败但没人知道"造成的，
> 而它已经让线上演示站落后了 4 个提交长达数天。
