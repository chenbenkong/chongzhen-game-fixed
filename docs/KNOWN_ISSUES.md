## 一、尚未修复的问题

### 1.1 · 第六轮已部分处理 · 首屏预取的分片数量从 46 降到 23

**位置**：`vite.config.js` 的 `manualChunks`（`historicalBucket` / `transitionBucket`）。

**原状**：Vite 把 17 个历史年份 + 18 个过渡年份各自分包，
而 `events/index.ts` 静态 import 全部，于是首屏一次性预取 **1.36MB / 46 个 JS 请求**，
线上 FCP 1.34s（本地 112ms，差异全是网络往返）。

**这一轮做了什么**：按本文原来的建议 —— 先合并年份分片，不动引擎的异步模型 ——
把每个年份一片改成「历史 4 年一片 / 过渡 5 年一片」。
产物 JS 分片从 **46 个降到 23 个**，总体积一个字节没变，
省掉的是 23 次请求往返，正是 FCP 差距的来源。

**仍未解决的部分**：这些分片**依然是全量预取** —— 因为
`events/index.ts` 是静态 import，`manualChunks` 只影响"切成几个文件"，不影响"何时取"。
要真正做到按需加载，必须把事件挑选改成异步，那会大改 `useGameEngine` 核心。
桌面版（Steam 的实际发行形态）跑在本地磁盘上，这个成本根本不存在，
所以完整的懒加载仍然排在低优先级。

**第六轮之后实测的准确口径**（`dist/index.html` 的 modulepreload 列表）：
首屏预取 **19 个 JS / 2.63 MB**。其中 `events-ending-*.js` 占 167 KB，
它**按定义无法延后** —— `data/boundaryEvents.ts` 必须静态拿到全部结局事件
逐个注册给 `BoundaryEventManager`，而引擎在任何一个月都可能抛出结局。
上一轮在 `events/index.ts` 末尾留下的注释声称"结局数据不再阻塞首屏"，
这是**错的**（本轮实测推翻并已改正）。同轮还删掉了该文件里一个
`import { allEndingEvents } from './ending'` 死引用 —— 它只被早已删除的
同名 export 用过，而 `noUnusedLocals` 没有报它（已用探针验证：往该文件追加一个
完全无用的 import，`tsc --noEmit` 依然通过）。
**结论：类型检查对"死 import"这一类是盲的，别把它当成防线。**

**第十一轮重新量过**：加进 8 条归零警告事件之后，
首屏预取变成 **20 个 JS / 2,698,132 B**，第十二轮加岁俸之后是 **2,698,429 B ≈ 2.70 MB**（+297 B）。
新增内容全部落在 `events-ending-*.js` 里（167 KB → **181,111 B**）——
`boundaryEvents.ts` 静态 import 这批警告事件，它们和结局是同一块，
这正好再次印证上面那句"结局数据按定义无法延后"。请求数从 19 变 20 是分片切法的连带位移，
不是新增了一个"警告事件专属文件"。
**第十三轮**给图鉴补了"罢黜归田"一格，同样落在这片：仍是 20 个 JS / **2,700,390 B**（+1,961 B），
`events-ending-*.js` 现为 **185,172 B**。
线上 FCP 第十轮实测 **244 ms**，仍然没有回到当年 1.34s 那个量级 ——
也就是说这一路减请求的改动是有效的，本文上面那句"完整懒加载排低优先级"照旧成立。

**本轮顺带修掉的真实缺陷（开发工具侧）**：
`scripts/validate-events.ts`、`scripts/audit-events.ts`、`scripts/audit-narrative-quality.ts`
三个事件体检脚本**全部在运行时崩溃** —— 它们都从 barrel import 那个已被删除的
`allEndingEvents`，拿到 `undefined` 后 `for (const event of events)` 抛
`TypeError: events is not iterable`。也就是说本文「需要人工验收的项」里
指向的那两条内容体检命令，其实从上一次性能改造起就一直跑不了。
三处已改为按路径直取 `../src/data/events/ending`，现在全部跑通且结论是干净的：
六个事件池 0 问题（标签与效果对账、空标题/缺描述/缺选项/条件矛盾/年份区间倒置）。

**并把这一类钉进 CI**：`tsconfig.test.json` 的 include 加上 `scripts/*.ts`。
改之前 `scripts/` 完全不在类型检查范围内，所以那次删 export 的改动才会一路沉默下来。
加上之后，同样的破坏会以 `error TS2459: Module '"../src/data/events/index"'
declares 'allEndingEvents' locally, but it is not exported` 直接拦住部署
（已实测：把 import 改回 barrel 形式，typecheck 立刻失败）。

**本轮新增的体检脚本**：`scripts/audit-flag-reachability.ts` ——
它把「事件条件要求的 flag」与「任何选项能获得的 flag」两张表对拍，
用来找"因前置 flag 永不可能获得而永远选不中的事件"。
当前结果：400 个事件里 **0 个** 这类死内容，0 个"只 remove 从不 add"的 flag。
另外 216 个 flag 属于"写进去但没有任何条件读它"（妻室线、党争立场居多），
是记账冗余而非缺陷，动它们等于发明玩法，故保留。
（这 9 个新出现的白存 flag 是第七轮把出身线 c3 的 `flags.add` 搬进 `effects` 之后
才第一次真的被写入存档的 —— 数字变大恰好是那处修复生效的证据。）

**第七轮补的第二个体检**：`scripts/audit-event-shape.ts`（`npm run audit:shape`）。
flag 可达性查的是"这条条件能不能凑齐"，它查的是"这个键名引擎认不认"，
两类问题互相覆盖不到。详见第三节第七轮。

### 1.2 · 本轮新增 · 长周目性能只做了推理、未做实测

本轮把引擎热路径从 O(n×m) 改成 O(n+m)（见 STEAM_RELEASE §2.6），
所以**理论上**不再随存档变老而劣化。但实测只覆盖了"单次推进月份"
（P99 16.8ms），**没有**跑一个长存档（200+ 条 `eventHistory`）来对比帧率。
这是推理，不是实测。

**建议验收方式**：用幽灵模式跳到 1644 年，积累大量事件历史后，
连续推进 12 个月并记录帧间隔。

### 1.3 · 遗留 · 成就数据仍是模块级共享状态（结构性重构未做）

**位置**：`src/types/achievement.ts` 的 `currentAchievementData`。

**现状**：成就数据仍保存在一个模块级变量里，而不是随 `SaveData` 传递。

**已解决的部分 —— 引用别名与退役 id 清理**：
原来 `setAchievementData` 直接按引用保存调用方的对象、`loadAchievements` 也按引用返回
内部对象，于是任何调用方的一次就地修改都会污染全局成就状态，而且完全不会报错。
现在读写边界上都做防御性拷贝；本轮又在同一个函数里加上了
`RETIRED_ACHIEVEMENT_IDS` 的剔除（已删除的成就不能留在旧存档里）。
行为由 `tests/unit/achievement.store.test.ts`（6 例）与
`achievement.steamLimit.test.ts`（8 例）钉住。

**仍未解决的部分**：模块级单例本身。它的实际影响只出现在
"同时存在多个成就消费者"的场景（多周目并行、回放、成就对比面板），
而当前游戏在任何时刻都只有一个引擎实例，因此这不构成现实缺陷。

**为什么不做完整重构**：把成就数据并入 `SaveData` 意味着
`unlockAchievement` / `checkAndUnlockAchievements` 都要改成由调用方传入并回传数据，
而它们目前被 `endingSystem`（不持有引擎状态）与多个组件直接调用。
这是一次横跨 4 个模块的改动，风险明显高于它现在能带来的收益。
**触发条件**：一旦真的要做多周目并行或回放，再动它。

### 1.4 · 第十一轮新增 · 模拟器实测出来、这一轮**没有**修的问题

第十二轮补上岁俸，同一份构建 A/B 100 局是 avg 32→35 月、触达 122→129/402、

是内容设计而不是对账，机器给不出答案。想推这个数，从小处推：
挑一条支线（情感线最集中，30 多条），把它内部该互读的对上，比全游戏撒一遍有效。

第十八轮的结论：**不用定，这条不是平衡问题。** 400 局实测（seed 1..50 × steady/warden × 四出身）

「三天后，李自成攻入北京」（1644 年三月）。玩家 1629 年读到这句话，不是难度高，是它在说一件还没发生的事。

中位 24 → 145 月，平均触达事件 77.9 → **125.1 条**，从四档里最短变成最长；

### 排查方法

"闪退"是个主观词，先要确定它指的是哪一种。三种形态、三种查法：

| 形态 | 判定方式 | 工具 |
| --- | --- | --- |
| 未捕获异常 | `page.on('pageerror')` | `tests/crash-hunt.mjs` |
| React 错误界面 | DOM 里有 `.error-boundary` | 同上 |
| 白屏 | `#root` 的 childElementCount === 0 | 同上 |

新增的三个可复用脚本（都在 `tests/`，需先 `npm run build && npm run preview`）：

| 脚本 | 作用 |
| --- | --- |
| `npm run test:crash` | 乱按压力测试：三连击选项与推进、结算进行中点别的、反复开关每个弹窗、存档往返、localStorage 写满后继续玩、中途刷新 |
| `npm run test:fuzz` | 存档模糊测试：**37 个畸形存档**（缺字段 / null / 字符串 / 超长 / 已删除的成就 id / 非法 JSON）逐一加载 |
| `npm run test:mem` | 内存与帧率：60 次弹窗开关后的堆占用、以及不同长度 `eventHistory` 下的帧间隔 |

### 找到并修复的真缺陷

| 严重度 | 缺陷 | 后果 |
| --- | --- | --- |
| **高** | `character` 存在但**整个 `attributes` 缺失**时，读档后渲染第一帧就抛 `Cannot read properties of undefined (reading '理政')` | **白屏**。抛在 AttributePanel（它直接下标访问 `attributes.理政`），整个游戏被 ErrorBoundary 接管 |
| **高** | 游戏内存档面板的「继续上次游戏」自己 `JSON.parse`，**绕过 `migrateSave`** | 同一个存档从标题屏读没事、从游戏内读就崩 —— 而这正是玩家最容易误触的路径 |
| **高** | `STORAGE_ERROR_EVENT` 一直在派发，但**没有任何组件订阅** | 文档里"存档失败不再静默"其实并不成立：localStorage 写满时玩家毫无提示地丢掉整局进度 |
| 高 | 存档损坏时「继续上次游戏」按钮直接消失，只有一条 console.error | 看起来像"存档被吃掉"，通常被当成丢档 / 闪退投诉 |
| 中 | Electron 主进程**没有** `uncaughtException` / `unhandledRejection` 监听 | 主进程任何未捕获异常都会让整个应用立即退出、无栈无提示 —— 这正是桌面端"闪退"的字面含义 |
| 中 | 没有 `render-process-gone` 监听 | 渲染进程 OOM 时窗口变白，玩家无法恢复也不知道发生了什么 |
| 中 | 启动流程失败只 `console.error` | 结果是"进程活着但一个窗口都没有"，玩家看到应用闪一下就没了 |
| 低 | `migrateSave` 只判 `!raw.character` 不判类型 | `character` 是字符串时抛 "Cannot create property 'hidden' on string"，虽被 catch 吞掉但日志误导 |

### 修复要点

`migrateSave` 此前为**每一个**字段都做了兜底，唯独漏了 `attributes`：

```ts
if (!Array.isArray(character.flags)) character.flags = []
raw.character.hidden = normalizeHidden(raw.character.hidden)
// ... 但没有 attributes，于是崩溃点被推迟到渲染期
```

现在：

```ts
raw.character.attributes = normalizeAttributes(raw.character.attributes)
```

`normalizeAttributes` 与 `normalizeHidden` 对称：缺键 / null / NaN 一律取默认值，
越界夹到 0–100。**关键在于它在读档路径上无条件执行** ——
渲染组件是直接下标访问属性的，兜底必须发生在数据层，不能指望每个组件自己判空。

### 验证结果

- 存档模糊测试：**37 个用例，0 崩溃**（修复前 1 个真白屏，外加 1 条绕过迁移的路径）
- 压力测试：11 次健康检查全绿，0 未捕获异常
- 内存：60 次弹窗开关后堆占用 5.5 → 6.1 MB **完全持平**，无泄露
- 帧率：注入 600 条 `eventHistory` 的长存档并不比 5 条的慢（样本偏少，仅作趋势参考）

### 两条方法论教训

**一、不要把"日志"和"崩溃"混为一谈。**
第一版检测器把**任何** `console.error` 都算作崩溃，于是报出"还有 3 个白屏"。
实际上那 3 个都是「存档损坏 → 被 try/catch 正确捕获 → 打一条诊断日志」，
root 完好、无 ErrorBoundary、无未捕获异常 —— 那是**正确行为**。

真正的闪退只有三种：`pageerror` / ErrorBoundary 接管 / `#root` 被清空。
混为一谈会让你去修不存在的问题，同时掩盖真正要修的地方。
这条已写进 `tests/save-fuzz.mjs` 的注释里。

**二、渲染早于 effect，只靠事件通知会漏。**
标题屏在**渲染阶段**就调用 `hasAutosave()`，而订阅事件发生在 `useEffect` 里 ——
渲染早于 effect，所以只在构造完成时派发的读错误事件会被整个漏掉，
提示永远不会出现。这正是"存档坏了却没人告诉玩家"的直接原因之一。
因此读错误额外在内存里留了一份供 UI 挂载时补取（`takePendingReadError`）。

## 三、已修复的问题（按轮次索引）

回归测试共 **310 例**，分 **35 个文件**，全部在 `tests/unit/`（另有 1 条默认关闭的槽位探针，`SIM_PROBE_SLOTS=1` 才跑）。

### 第二十轮：那条乞休/致仕支线为什么播不出来 —— 不是门槛高，是那一层分不到槽

入口是 §1.4 ⑯ 里刻意没加工成结论的第 1 条事实：那批事件的年窗最早开到 1635（第 84 月），
可实测里播出月份全挤在 159 / 163 / 187 三个点上，"没有任何年代闸把它们挡在 1641 以前，可就是没有更早的一次"。
⑯ 当时留下的判据是：**分清"门槛太高"与"池子里抢不过别的事件"**。这一轮查清了，是后者，而且比"抢不过"更糟。

#### 一、机制：`random` 是兜底位，而全部 21 条 `route_*` 恰好都在那一层

引擎每月的**主槽**按 `historical/chain（未看过）→ transition（未看过）→ random` 顺序填，
`random` 只在**前两层全空**时才拿得到槽（`useGameEngine.ts:1015`）。把 20 局、共 3850 个月的
"这个月的主槽落在哪一层"逐月打出来（修复前）：

| 主槽归属 | 月份 | 占比 |
| --- | --- | --- |
| historical / chain | 680 | 18% |
| transition | 3071 | 80% |
| **random** | **19** | **0.5%** |
| 只剩支线池（branch） | 80 | 2% |

**这张表现在能重跑**：`SIM_PROBE_SLOTS=1 node node_modules/vitest/vitest.mjs run tests/unit/simulation.routeGuide.test.ts`
（同口径 20 局 warden × 缙绅）。修复后它打的是 `3834 个月：hist+chain 681(17.8%) · transition 3068(80.0%) · random 0 · 只剩支线 85(2.2%)` ——
`random` 归零正是本轮的结果；要复现上面那行 0.5%，把 `route_guide.ts` 里 21 个 `type: 'transition'` 改回 `'random'` 再跑一次。

而**每月主池**（`ALL_EVENTS`）里 `type:'random'` 的事件**只有 21 条，恰好就是全部的 `route_*` 结局引路事件**。
（`boundaryEvents.ts:625` 与 `zeroWarningEvents.ts:552` 那两条也写着 `random`，但它们走的是归零警告/边界检查那条路，
不占主槽，本轮没动。）所以 ⑯ 的现象不是门槛：**条件是满足的，只是永远轮不到**。它们能播的那几个月（159/163/187 = 1641-04 / 1641-08 / 1643-04）
正是"当年的大事件已被抽干、前两层同时为空"的月份 —— 换句话说，玩家要活到把 transition 池抽干，
才第一次有机会看见"你可以致仕"这个选项。连带后果在结局层：这批事件是 `急流勇退`/`主动致仕`/`著书立说`/
`辞官`/`归隐`/`积劳成疾` 这些经历的**唯一写手**，善终结局与图鉴那几格读它们 ——
"事件层饿死"于是表现成"结局层不可达"（⑮ 数出来的那五条点不亮的善终，根子在这里）。

#### 二、修法：把 21 条改回它们本来的分类，不动引擎的抽取顺序

| 文件 | 改动 |
| --- | --- |
| `src/data/events/transition/route_guide.ts` | 21 条 `type: 'random'` → `type: 'transition'`，头部注释记下分层规则、`useGameEngine.ts:1015`、3850 个月的实测与"为什么改数据而不是改引擎" |

#### 三、修完立刻冒出来的新问题：同一个坝在 1635 年复现（本轮 B）

改完分类，立刻拿**同一批 400 局种子**重跑（不是只跑 12 局的取样），形状变了：
`殉职任上`（`ending_duty_death`）从 7 局涨到 **37 局、平均触发局长从 162 月掉到 90 月**（= 1635 年七月），
`流亡海外` 从 6 局涨到 **25 局** —— 一年吃掉 36 局，平均局长掉约 10 个月，1644 从 185 局掉到 137 局，
"活到 1636 年以后"只剩 165/400 = 41%，贴着 0.4 的棘轮。

这不是新缺陷，是**第十九轮 ⑬ 的同一类缺陷换了个入口**：判定读的是 flag + 状态，
`鞠躬尽瘁` / `转移资产` 一旦写上、状态一凑齐就恒真，年窗一开的第一次月份推进必然命中，
玩家没有被问过就把局收走了。之前它量不出来，只因为门票事件（`route_*`）根本播不出来。

### 第十八轮：去查一条出身问题，结果拆掉了一座水坝 —— 400 局里没有一局玩进 1636 年

入口是 §1.4 ⑩（`诗文清望` 的一局明显比别的出身短）。第十五轮把它当成数值平衡挂在那儿，
等一句"每种出身该活多久"。这一轮去查它，查到的答案是：**它不是平衡问题，而是一条不读年代的判定**；
而顺着它往下打印终局年份分布，逮到的缺陷比它大一个数量级。

#### 一、⑩ 的真根因：一条 S 级结局的 `check` 读都不读 `currentYear`

《东林烈士》（`faction_donglin_martyr`）的判定是「东林好感≥80 ∧ 阉党≤20 ∧ 东林死忠/复社成员 ∧ 清议≥60」——
四个子句全是**状态**，没有一个是历史。`诗文清望` 开局清议 60、带着「党争漩涡」被强制卷进东林线，
是最快踩齐这四条的出身，于是 100 局里 21 局在**平均第 13 个月**被这条结局收走。
而它自己的文本写的是「三天后，李自成攻入北京」—— 那是 1644 年三月的事。
玩家 1629 年读到这句话，不是难，是这句话在说一件还没发生的事。

同一份文件里其实早就有下限：阈值结局走 `pastGrace`（12 个月宽限期），编译器包装的叙事结局走
`NARRATIVE_MIN_YEAR / NARRATIVE_MIN_TURN`。**只有手写的那三条什么下限都没有。**
修法不是再发明第三套下限，是把那两个常量导出、让手写的 check 也复用同一个原则，
再加一条"文本绑定在哪一年，闸门就至少开到哪一年"：

```ts
function settledIn(params: BoundaryEventCheckParams, minYear: number): boolean {
```

数据体检全绿：形状 DEAD 0、承诺/兑现 402 条事件 / 1465 个选项 0 问题、
值域 0、永锁选项 0、出身无出路 0、出身门互相抵消 0、门槛文案漏机器 id 0、
违例人名 0、重复键 0、假门槛 0、履历表无死文案。

### 第十六轮：把"经历"演到玩家眼前 —— 447 条里的 250 条暗账，先用第二把尺子量一遍

入口还是 §1.4 ⑧ 里那条我自己标了"改的是 UI 所以没动"的出路。第十五轮把因果网接起来之后，
剩下的事实很难看：**250 条写了没人读的经历**，玩家点了那一下，游戏里除了门槛没人知道。
给它们找下游读者是内容工程，短期内做不完；但"没人读"和"没人看得见"是两件事 ——
后者只需要一张履历表。这一轮做了后者，并且**没有因此改动前者那把尺子**。

#### 一、先量哪些 flag 真的会被玩家带在身上

履历表不能按"全游戏有哪些 flag"来写文案，得按"玩家实际走过哪些"来写。
静态对账给出的 250 条白存里，一大批根本撞不上：`simulate.ts` 跑 warden / steady 两组各 100 局，
**warden 组有 143/250 条一次都没被带上身，steady 组 130/250**。给这些写文案是给自己找死文案。
所以名单取自"两组合起来真被带过"的那一百来条，按携带次数排序，取了 96 条
（`tests/unit/flagMemoirs.data.test.ts` 里 `MOST_CARRIED_DEAD_FLAGS` 钉住其中 31 条最高频的，
测得于 2026-10-16，200 局）。

#### 二、`src/data/flagBiography.ts`：flag → 一句履历

三条规则写在文件头，都是量出来的教训而不审美：
1. **只给玩家真会带在身上的经历写文案**（见上）；
2. **没登记的经历一律不显示** —— `wife_wangshi`、`pending_zhanggui` 这批是机器 id，
   原样吐到界面上就是"角色页写着 xianv_info"那种笑话，所以 `memoirsOf()` 丢弃未知键，
   UI 测试用一个不存在的 flag 名钉住这条；
3. **文案必须忠于写出它的那个选项**。`卖人求安` 写"供出她藏身的地方，换一日平安"，
   不写成"与红袖诀别"—— 履历是判词，不是二次创作。

分四组：朝局 / 风骨 / 家宅 / 人情（`MEMOIR_GROUP_ORDER`）。组内按获得先后排，
组按固定序出，空则整组不出现。

#### 三、UI：生平回顾里加一格「这一生」

没有新弹窗、没有新页面 —— 在既有的 `LifeReview` 标签组里插一格，位置紧跟「生平大事」。
一行 lede（`拣出可记者 N`）+ 分组列表，宽屏两栏、≤600px 收一栏，配色沿用金/褐那套。
结算页（`GameOverScreen` 的「查看生平」）和死亡结局关闭后的自动跳转都能进 —— 那条通路本来就有。

#### 四、第二把尺子，故意不和第一把合并

`audit-flag-reachability.ts` 现在同时报两个数：

- **玩法回读率 197/447 = 44.1%** —— 口径原封不动，还是"被某个门槛读过"。
  这一轮**没有**把它调高，因为履历表不是因果。
- **玩家可见性 65.5%**（新增 `visibilityRate`）—— 门槛读 ∪ 上履历表。
  配套的棘轮是 `invisible ≤ 160`（实测 154）：既没门槛读、又没上履历的那部分，
  对玩家等于没发生。`WRITE_ONLY_CEILING = 250` 一个字没改。

两条 CI 断言防的是同一种赖账：**把"看得见"洗成"有人读"**。
`flagMemoirs.data.test.ts` 里那条恒等式 `已上履历的死条子 + invisible === writeOnly`
只有在两把尺子各自干净时才成立；`deadMemoirs` 必须为空（登记了却全游戏没人写得出的文案 = 假履历）。

#### 五、浏览器实测（不是只有 jsdom）

本地 `vite` 起服，真点：定名字 → 选寒门 → 一路推到崇祯十七年。
**十七年二月**那场「宣府塘报」四个选项里只有【投降保命】可选 —— 另外三个被第十五轮接上的
选项级门槛锁住并写明理由，这就是那套闸门在真实一局里的样子。选了投降，
死于**开门投降，背主求荣**，结算页「查看生平」→「这一生」：
四个分组 16 条履历，`拣出可记者 16` 与列表条目数一致；身上另带着 `origin_hanmen_001_done`、
`归零警告·体质` 这类机器名目，界面上一个字也没漏出来。五个标签轮切不串台。
小窗（531px）实测走的是单栏分支，两栏由 CSSOM 里的基础规则与 `@media (max-width:600px)` 对照确认。

顺带记一条工具坑：内嵌浏览器 surface 不可见时 `visibilityState=hidden`，
定时器被节流到 ~1s/次，自动点月在隐藏页面上会慢到不可用（且截图接口直接拒绝）。
这一轮的"推到十七年"是靠改 `chongzhen_autosave` 里的年月跳过去的，
不是靠耐心；跳转只改了时钟与属性，走的事件、门槛、结局都是引擎真算的。

#### 六、还欠着的

⑧ 的另一半没动：**回响池产出的 71 条里仍只有 8 条被别人读走**，
把经历显示出来并不使它们变成因果。⑨ 的 250 条白存也**一条没减**，只是其中 96 条现在看得见了。
余下 154 条 invisible 里，「宣府塘报」那一场四个选项写的 `死守宣府` / `诈降反戈` / `撤退保卫北京`
这批**抉择现场**级 flag 值得先看 —— 那一局玩家亲手选过的事，履历上一条都没有；
它们和已经上表的 `独对之荣`、`平台三策` 同属"一局只发生一次但很能定义这个人"的那类。

### 第十五轮：写了没人读的经历 —— 447 条 flag 里 250 条是死条子，以及"记忆回读率"这把新尺子

这一轮的入口是运营侧点的名：从影响最大的第 3 项开始做 ——**事件没有记忆**。
玩家在某年救了一个人，十年后这件事对游戏没有任何影响。

先把它量出来。`character.flags`（"经历"）在这个游戏里**只有一个读者：门槛**。
翻遍 `src/`，组件不显示它，传记不引用它，除了存档读写没人碰它。
所以"某个选项写了一条 flag，而全游戏没有一处门槛引用它"不是洁癖问题，
是**玩家那次抉择等于没发生过**。静态对账下来：447 条可写经历里 251 条只写不读，
**记忆回读率 43.8%**。

#### 一、选项级门槛先变成真的，尺子才能换口径

`choices[].showConditions` 从前是**装饰** —— 引擎只按事件级 `conditions` 决定事件能不能播，
选项上写的 `flags` / `rank` 门槛根本没被执行（`EventDisplay.tsx` 里那份判断只用来把选项画灰）。
这一轮把它接进引擎，代价是必须同时防住软锁：一个事件所有选项都被锁住时玩家点不动，
所以 `hasOpenChoice` 决定事件级准入。三处代码（引擎选事件、UI 灰条、模拟器选路）
从此共用 `src/utils/choiceRequirements.ts` 里的一把尺子 —— **搬出来而不是复制一份**，
因为复制一份就等于用两套规则跑同一批数据，测出来的覆盖率是假的。

配套体检：**`scripts/audit-choice-lockout.ts`**（`npm run audit:lockout`）报 `DEAD_OPTION`
（选项级门槛要求一段全游戏写不出来的经历 → 这个选项对所有人永久消失）。
它和 `audit-flag-reachability.ts` 的事件级 `any` 规则是同一件事的两半，
刻意分开而不合并：合并过一次就会在两处漂移。

口径跟着换了：读门现在 = 事件级 `conditions.flags` ∪ 选项级 `showConditions.flags`，六个子句全算。
**这一条有测试钉着**（`readBy` 里必须至少出现一处"选项级"引用）——
否则下一个改数据的人会把整套接线工程统计成死条子。

#### 二、回响池：只读的下游，专门接住老内容写出去没人收的经历

`src/data/events/echo/`（18 条事件，5 个文件）是这个项目里唯一**只读不写老 flag** 的一池：
每条都以"玩家确实有过某段经历"开门，把那段经历演成后果。
`echo_*_done` 是这一池自己的一次性开关，写在 `notHas` 里，不算是产出。

契约由 `audit.flagReachability.test.ts` 钉三条：每条回响必须以正子句开门、
开门经历必须由**别的**事件写出（不许自锁）、产出至少 5 条被下游读走。

实测（100 局，含 warden 的苟活组）：18 条里 15 条真的被玩家撞见，每局播出 1.99 次。
没撞见的 3 条不是死代码 —— `echo_faction_002` 单拎出来跑 250 局寒门能播 14 次，
只是样本里没有；这一池的开门 flag 现在**没有一个**是全游戏无人书写的。

#### 三、诚实的负收益：死条子从 9.8 涨到 12.0 个/局

回响池自己写了 71 条经历，其中只有 8 条有下游读者 —— 也就是说这一轮**净新增约 63 条死条子**。
老内容那边确实被救回来 27 条（白存 215 → 188），但抵不上自己造的。
随身死 flag 从第十四轮基线的 9.8 涨到 12.0。

这个数字**没有被调小**，只被钉住了：`WRITE_ONLY_CEILING = 250` 是棘轮，
想调它就得先回答"这条 flag 谁来读"。真正的解法写在 §1.4 ⑧⑨：
要么给回响产出找下游读者，要么把"经历"显示到界面上，让它不再是只有门槛能看见的暗数据。

#### 四、71 处假门槛清零（三类去处，别一律删）

负面子句（`notHas` / `none`）里引用了全游戏没人写得出的经历 = 条件恒真 = 没有闸门，
只有下一个改数据的人会被骗。分三类处理，**不是一律删掉**：

1. **拼错的别名 → 改名**。`隐居山林` 没人写，`归隐山林` 有人写（`historical_018/c5`、
   `historical_019/c3`），12 处排除改完才真的生效。
2. **同一数组里已有可写兄弟覆盖 → 删**。删掉装饰项不改变判定。
3. **同一事件内结构上不可能成立 → 删**。事件一次性，选项 c1 写的 flag 不可能在自己
   c2 的 `notHas` 里挡住 c2 —— 那种互斥是结构给的，写 flag 只是假装把关。

改完 `audit-flag-reachability.ts` 报：永不可满足 0、`orphanRemove` 0、假门槛 0，
回读率升到 **197/447 = 44.1%**。这三条现在都是 CI 断言。

#### 五、两个踩到的坑（都值得写下来）

**codemod 留下的数组空洞。** 批量删元素用正则清理 `''`、`,,`、`, ]`，
但漏了"行首只有一个孤立逗号"这一种，于是造出 `[, '出家', …]` 这样的 **array elision** ——
JS 里它是 `undefined`，体检立刻报出 4 处「undefined」假门槛。修法：手工补 3 处，
**而不是再写第三版 regex**。教训是：codemod 之后必须重跑体检，不能相信替换次数。

**差点把取样口径当成回归。** 改完数据复测，平均局长从 43.5 个月"腰斩"到 23.5 个月，
第一反应是改名激活的 12 处排除把结局改坏了。验证方式是把这一轮的三个数据文件
反向 patch 回改前再跑同一批种子：**两次的每个数字都完全一致**（只有白存 251→250 之差），
差异其实来自策略组 —— 上一批用的是 `warden`（不惜代价苟活），这一批改成了 `steady`
（看见会收尾的选项就绕开）。同 build 补齐 warden 组后是 39.3 个月，与 43.5 同一量级。
**跨轮比局长，先对齐策略组**；`simulate.ts` 用种子替身劫持 `Math.random`，
任何一处可用性变化都会重排整条随机数流，具体路径本来就不可比。

顺带量到一个失衡（见 §1.4 ⑩）：`诗文清望` 出身平均局长最短（steady 组 13.6 月，
其余出身 22.5 / 27.3 / 30.2）。

### 第十四轮：一整条灰色支线是死的 —— 三条"引擎自己作废自己的规则"，以及一个自己骗自己的基线

这一轮的入口是运营侧的诉求：事件是这个项目占比最大的内容，而玩法要更完整、更流畅。
于是先做两件事 —— 兑现灰色支线里那 9 条"徽章写着收钱、账户一动不动"的选项（见 §本末），
再补三条**有代价的回升通道**（中官 / 体质 / 士绅，从前这三项只有下降通道，掉下去就再也回不来）。

补完之后拿同种子跑 N=100 复测，数字反而**崩了**：平均局长从 12 局取样看不出问题，
放大到 100 局之后是 12.7 个月，破产占 77%，新通道吃掉 94.4% 的支线名额。
顺着这条线往下挖，挖出来的不是一处平衡问题，是**四类"从来没被放在一起比过"的东西**。

#### 一、52 条灰色事件里 37 条被钉死在某一年

真正的原因不是事件太贵，是**它们根本没出现的机会**。
旧数据里 37 条灰色事件写着 `year: { min: 1639, max: 1639 }` —— 一年、只此一年、错过不再。
游戏从 1628 年起算，玩家能活到 1639 的局本来就是少数，于是：

- 一条要"先有钱"的贪腐线，`bribery` / `smuggling` 的**正增量选项整条线的实测触达率是 0.00 次/局**；
- 新加的三条回升通道没有年份门槛，于是它们把 94.4% 的支线名额全占了 —— 不是它们太强，是对手根本没上场；
- 玩家看到的现象是"钱只出不进"，而这不是数值问题，是**门控问题伪装成了数值问题**。

修法是把 37 处单一年份钉死全部拆掉（`min == max` 的那种），只保留一条有剧情理由的：
`gray_fortune_001` 的谶语点名"崇祯九年，龙归大海"，那条必须写在 `year: { max: 1636 }` 之内，
否则天机说破了还播出来就是死信。

这条边界不能只靠"这次改干净了"，所以立了体检：**`scripts/audit-repeatable-gating.ts`**
（`npm run audit:gating`）—— 可重复池（gray / character / national / faction）里
不许出现 `min == max` 的单一年份钉死，也不许出现晚于开局两年以上的年份下限
（那种门槛等于"这局大概率看不到"）。月份窗口不查：季节是节令，不是年份锁。

反空跑同样是硬断言：合成池里必须**恰好**逮住那两条该逮的，
而且不许误报只有月份的事件、只有 `year.max` 的事件、以及一次性 `transition` 事件的年份钉死。

#### 二、23 条事件在卖玩家买不起的东西

拆掉年份锁之后复测，局长 18.5 个月、破产仍然 36%。这一次把"前 18 个月里，
每类事件平均抽走多少财帛"摊开看，最上面几行是这样的：

| 事件 | 最贵那个选项要付 | 事件条件要求的财帛下限 |
| --- | --- | --- |
| `gray_debauchery_021` | 60 | 50 |
| `gray_debauchery_008` / `024` | 50 | 0 |
| `gray_debauchery_006` | 50 | 30 |
| `gray_reform_004` | 12 | 0 |
| `gray_patronage_002` | 11 | 0 |

**可重复事件每 6 个月就会重新上门一次。**门槛低于售价，就意味着一个已经囊空如洗的人
还会不断被邀请去花他付不起的钱 —— 效果夹到 0，这条通道本身就成了压垮财帛的那只手。
我新加的三条"有代价的回升通道"恰恰是重灾区：它们的设计意图完全正确（白拿的康复没有意义），
但代价收得太狠，狠过它们所救的那三种死法。

规则定成一句：**回升通道要收钱，但它不该向付不起的人开张。**
23 条全部补上门槛（缺 `attributes` 的连块新建）。

同一份扫描跑全池会得到 174 条"违例"，其中 151 条在 `historical` / `chain` /
`transition` / `emotion` 里 —— **那些是史实节点上必须付的钱**：一次性剧情写"你捐五十两劳军"，
钱不够也得给，那是设计者要的代价。所以这条规则刻意只管可重复池，
并且把这条边界也写成用例（`tests/unit/eventAfford.audit.test.ts` 第三条：
合成的 `historical` 事件不许被报警，同时真池子里确实存在 >100 条这类一次性高消费 ——
否则"豁免"可能只是扫描器根本没看见它们）。

门槛会不会把这 8 条最贵的重新变成死内容？实测过了，没有：

| | random N=100 出现次数 | warden N=40 出现次数 |
| --- | --- | --- |
| `gray_debauchery_008`（门槛 50） | 9 | 60 |
| `gray_debauchery_021`（门槛 60） | 3 | 63 |
| `gray_debauchery_006`（门槛 50） | 35 | 185 |

穷官一年碰不到两回，富得流油的守成玩法平均一局撞两次 —— 这是**按财富分发内容**，
不是锁死内容。

#### 三、三条引擎自己作废自己的规则（K-14a / K-14b / K-14c）

数据改完之后，革职结局仍占 49%。这一次问题在引擎里，而且三条都是"两条规则打架，其中一条悄悄吃掉另一条"。

**K-14a · 考核没有上任缓冲。** `checkDemotion` 从 `turn = 0` 就开始判，
而四种出身里有三种**开局就落在某条革职条件之内**（寒门开局 体质 10、缙绅开局 圣眷 34 这一类）。
于是"第一个月就被罢职"是必然事件而不是风险。补了 `DEMOTION_GRACE_TURNS = 12`：
先让人真正上任一年，再让考核杀人。这个常量和灰色支线的年龄感是同一套判断，不是两个数字。

**K-14b · 道德归零有两条判死通路，其中一条不问警告。**
`boundaryEvents` 的 `moral_degeneracy` 要求先收到「归零警告·道德值」才判死（第十一轮的规矩），
而 `checkDemotion` 里 severity 3 的「道德败坏」**同一维度、不问警告、直接革职**。
两条规则同时存在等于第一条从未生效 —— 实测 49% 的局在第 10 个月被第二条直接收尾，
玩家连"你已经丧尽天良"这句提示都没见过。现在两条通路同进同退（读 `zeroWarnFlag('道德值')`）。

**K-14c · crisis 临界事件完全不吃冷却。** 引擎里那张 `cooldowns` 表头写的是「冷却期（月）」，
但它只管支线池；而 crisis 的条件判的是**状态**（`0 < 体质 < 20`）不是历史，玩家一直病着就恒真。
seed=8 实测「重病缠身」在**第 12 月和第 15 月各发作一次** —— 太医前一个月刚说"需静养数月"。
修法是把表提升到模块级 `EVENT_COOLDOWN_MONTHS`，支线池与 crisis **共用同一张表、同一份月份轨迹**，
并把判定收进一个函数 `crisisEventMayShow`（挂载路径与 `checkBoundary` 以前各写一份概率门，
正是"两处漂移"的老病灶）。归零警告仍然**必到**：不吃概率门也不吃冷却，理由和第十二轮一样。

三条都用变异测试反向验过：把 K-14c 那行冷却判断删掉，
`engine.boundary.test.ts` 立刻报 `seed=8：第 12 月 → 第 15 月，同一场病隔了 3 个月`（改回来又绿）；
K-14a/K-14b 的变异在上一节段落里已记（同一批用例）。

#### 四、欲望值是一个只进不出的棘轮

账面体检（`audit:economy` 那一类，本轮扩到隐藏维度）跑出来的聚合值是
**欲望值 进 12.47 : 1 出** —— 全仓 296 个选项加欲望值，只有 47 个减。
欲望只涨不跌意味着它是**一颗定时炸弹而不是一个资源**：涨到阈值就撞上「贪墨被查」，
而玩家无论怎么选都降不下来。

补法是新增一条灰色支线 **`src/data/events/gray/reform.ts`**（`gray_reform_001..005`，15 个选项）：
清丈田亩、疏河赈灾、整顿驿传这一类"做事"的事件，用**道德值与理政**换欲望值的回落。
刻意留了 4 个加欲望值的腐败选项（合计 +48），否则这条线会变成无代价的赎罪券。
比率从 12.47 降到 **7.85**（进 296 条共 +3564 / 出 47 条共 −454）。

#### 五、出身不是风味，是死因

第十一轮起模拟器就能跑完整局，但它**一直只测寒门** —— `simulateRun` 根本没有 origin 参数，
于是一整类开局缺陷不属于"没测到"，而是**结构上测不到**。给 `simulateRun` 加上 origin
之后跑出身 × 策略矩阵，四种出身呈现出完全不同的死法（诗文清望死于党争与中官，
缙绅死于道德与革职），并把几项开局资源抬到地板之上：
寒门 财帛 25 / 圣眷 26 / 中官 22 / 士绅 22，诗文清望的 体质 44 / 欲望值 24（唯一一个
开局就落在奢靡线 25–35 门槛之下的出身，所以那条线的触达率本来就该由它兜底）。

3. 触达率下降 37.6% → 38.5%（random 持平）而 warden 从 68.0% 掉到 44.1%，

   不是新内容挤掉了旧内容。本轮新增 20 条事件反而让分母从 359 涨到 379。
4. 死亡结构变了，而且变得更合理：基线是「中官 39 + 士绅 27」这两种**没有回升通道**的死法占七成；
   本轮是「革职 29 + 士林唾弃 22 + 破产 18」，且七种结局都还有局走到。

### 第十三轮：结局图鉴上那 11 格永远点不亮的灰

第十一、十二两轮把"整局能不能跑完"机器化了之后，第十二轮顺手量出来一条孤立缺陷
（图鉴里没有"革职为民"这格）。这一轮去查它为什么能存在这么久，挖到的是一整片：
**结局的 id 有三套互不相认的命名**，而"哪些格子已经点亮"是把成就 id 砍掉 `_done`
直接当事件 id 猜出来的。三套 id + 一个靠猜的映射，从来没有放在一起比过，
所以坏掉的方式不是报错，是**界面安静地少亮一格**。

实测出来的账（`npm run audit:codex`，本轮新增）：

| | 数量 | 说明 |
| --- | --- | --- |
| 图鉴格子（`allEndingEvents`） | 43 → **44** | 本轮把"罢黜归田"补进去 |
| 结局成就（`ending_*_done`） | 34 | |
| **有格子、没有任何成就指向它** | **10** | 全是 `triggerable_*` 边界结局，以前**永远灰** |
| **有成就、但 id 对不上格子** | 1 | 破产：成就判据硬写 `ending_bankrupt`，格子叫 `triggerable_bankrupt`（引擎 `withEndingId` 会改名） |
| **成就点得亮、图鉴根本没这格** | 1 | `ending_demotion`：整段结局内联在引擎里 |

也就是说玩家能达成 44 种结局，图鉴上有 33 种会亮。剩下 11 种打出来了、
成就也弹了，图鉴上那一格却一辈子是灰的 —— 这不是数据缺失，是**没有对账点**。

**修法（刻意不加成就、不动 Steam 那 100 条上限）**：
1. `src/data/endingRegistry.ts` —— 唯一的换算点。`resolveEndingTileId(id)` 把引擎
   改名过的 id 映射回格子（`ENDING_ID_ALIASES` 一张小表，现在只有破产一条），
   认不出的返回 `null` 而不是"猜一个接近的"。
2. `AchievementData.reachedEndings` —— 存档里新增"本局真正达成过哪些格子"的记录，
   由 `triggerEndingAchievements` 用**换算后的格子 id** 写入，只记首次。
   图鉴点亮 = 成就反推 ∪ 达成记录，成就那份的时间戳优先（玩家看得见的那份是成就）。
   为什么非要和成就解耦：成就有 100 条硬上限，而"打过"这件事本身不需要名额。
3. 引擎里那 32 行内联结局搬进 `src/data/events/ending/endingsDemotion.ts`，
   两支（革职为民 / 流放边疆）**共用一个 id**，因此只占一格 —— 与成就
   `ending_demotion_done` 的口径完全一致，三方这才对上。
   搬的时候补了 `description`：人物志最后一段就是它的值，以前内联那份写的是空串，
   等于传略结尾白了一块。
4. `EndingCodex` 的推导从 `useEffect` 里提成导出的纯函数 `buildUnlockedTileIndex`。
   **这段以前写在 effect 内部，正是"猜错名字没有任何东西会红"的原因**；
   现在纯函数能用真组件直接压。
5. `scripts/audit-ending-codex.ts` + `npm run audit:codex`：把上面那张表变成断言，
   11 类问题（重复格子 / 分类或档位越界 / 格子渲染不出来 / 成就判据解析不出 id /
   有成就无格子 / 有格子无成就 / 已知名单过期 / 别名悬空或多余 / 边界事件无格子）。
   老规矩：脚本导出纯 `scanEndingCodex()`，CI 跑的是断言它为空的那条用例。

**顺带修掉的两个口径漏洞**（都是这一轮的意外收获）：
- `simulate.ts` 以前也自己硬写了破产那条别名，现在走同一个 `resolveEndingTileId`。
  于是第十一轮"死于归零必须先见过警告"那条不变量**第一次真的覆盖了财帛归零** ——
  以前破产局的 `endingId` 是 null，压根没进那条断言。
- 第十二轮加的 `KNOWN_UNREGISTERED_ENDINGS` 记账名单删掉了。留着它等于给以后
  "再往引擎里内联一段结局"开一条没人检查的通道；根因修完之后，
  走到未注册结局必须让 CI 直接红。

**取样宽度这件事必须说清楚**：`ending_demotion` 这条分支在默认 12 局里未必出现
（第十二轮是 16 局里撞出 2 局才看见的），所以本轮把 5 个**实测固定种子**
（1 / 2 / 3 / 4 / 7）写进用例，并要求取样里**必须同时含**改名过的破产与革职结局 ——
换种子测不到这两条时用例会直接失败，而不是悄悄空跑。

**新回归**：`tests/unit/endingCodex.registry.test.ts`（26 例）—— id 对账表 4 例、
革职结局搬进 data 3 例、点亮口径 4 例、达成记录与成就解耦 4 例、
真组件渲染 5 例、存档 JSON 往返 2 例、体检脚本 2 例、**真引擎跑完整局再到图鉴亮格** 2 例。
其中最后那组是唯一穿过真引擎的：`handleChoice` 打到 `handleGameOver`，
让引擎自己改名、自己调 `triggerEndingAchievements`，再回头看图鉴
（5 局 0.59 秒，断言"达成的格子集合 == 达成记录的键集合 == 亮起的格数"）。
`achievement.store.test.ts` 另加 3 例盯 `reachedEndings` 的读写边界拷贝、
旧存档缺字段、只记首次。

**线上/构建侧验证到什么程度（说清楚边界）**：`vite build` + `vite preview` 在真浏览器里
走完创建角色 → 进游戏 → 幽灵模式 → 结局图鉴，列表里**确实是 44 张卡**
（`endingRegistry` 新加的那条 import 没有把生产分片的模块图弄断，这是必须实测的一件事）。
但"打一局真结局再看格子亮没亮"这一下**没在浏览器里点出来** ——
`CheatMode` 的结局卡片双击只做预览（`handleEndingDoubleClick` 只 `setSelectedEvent`），
幽灵模式没有触发结局的入口，真打要几十个月。这一段改由上面那组真引擎用例压住：
它们跑的是同一个 `triggerEndingAchievements` → `recordEndingReached` → `buildUnlockedTileIndex`
链路，只是渲染环境是 jsdom。**浏览器里缺的只是"生产包 + 真点击"这一层。**

**代价**：首屏负载 20 个 JS / **2,700,390 B**（+1,961 B）。

`data/boundaryEvents.ts` 要静态拿到全部结局事件逐个注册给 `BoundaryEventManager`，
理由和实测口径都写在 §1.1，不是本轮新引出来的耦合。

### 第十二轮：官俸这条管道根本不存在 —— 以及"通知必达"

上一轮的模拟器留下了一个明确读数：**16 局守成玩法里 `财帛` 的声明净增量是 −0.77/月**，
于是 8/16 局一路掉到 0、死于「倾家荡产」。逐维对照 `declaredDelta == actualDelta`
已经排除了引擎暗扣，所以原因只能是另一个：**数据里有 369 个选项在往外扣财帛、240 个在给，
而"当官有俸禄"这条进钱管道在引擎里一条都没有**。
`audit:economy` 也从同一头印证过：财帛在 1633/1638/1643 三个窗口都是「正增量补不上负增量」。
静态审计十轮都看不出这条 —— 缺的不是坏代码，是**一整类代码从来没写过**。

**改了什么（引擎侧，一处）**：`annualStipend(rankName)` + `handleNextMonth` 里跨年结算。
每年正月按 `RANKS` 的 level 发一次俸银（七品 6 两/年，正一品 18 两/年），
走 `ATTR_BOUNDS.财帛` 的 0..100 裁剪，非官员身份（rank 不在表里）拿 0。
两个口径上的刻意选择：
- **只补约一半缺口**。把月薪开到盖过出血点会让破产结局整族见不到 ——
  `财帛` 上限只有 100，收入一高就长期顶格。现在的量级是"省着花能活、随便花照样破产"。
- **按年发而不是按月发**。推进月份时一次调用可能连跳最多 12 个空月，
  按月发会让"连跳"和"逐月点"两种手感在数值上不等价；
  在循环里数跨了几次年，两种点法就恒等价了（不变量：**发俸次数 == 跨过的年数**）。

**顺手补的第二条：岁俸要留痕。**
发钱不能又是一笔暗账 —— 第十一轮的教训正是"归零无声"。跨年结算时同时写一条生平
（`type:'choice'`、标题「支领岁俸」、`attributesChange.财帛` 记下金额），
史馆《生平》时间线里查得到哪一年领了多少；用例断言
"生平里『支领岁俸』的条数恒等于跨过的年数"，所以留痕和入账不可能一边有一边没有。

**顺手补的第三条：归零警告不再吃概率门。**
上一轮把判死改成"归零两次才要命"之后，警告本身仍然走 `checkByType('crisis')`
再乘 `CRISIS_EVENT_PROBABILITY = 0.3`。这留下一个悬空态：
某维归零后一直抽不中警告 ⇒ 第二道闸门永不满足 ⇒ **既不判死也不给救**，整局卡死。
`isZeroWarningRegistryId()` 把它从门里摘出来（推进路径与挂载路径两处同规则），
前缀常量与生成 id 同源，不会漂。
`serious_illness` 这类普通 crisis 仍然吃概率 —— 有反向用例钉住
"同一条随机数 0.99 下重病不出、警告出"。

**实测收益（A/B 各 100 局 steady，同一份构建只开关这两处）**：

| | 局长 avg / max | 触达事件 | 倾家荡产 | 终局归零前三 |
| --- | --- | --- | --- | --- |
| 关掉岁俸与警告豁免 | 32 / 89 | 122/402 | **24 局** | 中官×50、财帛×26、士绅×16 |
| 第十二轮（都开） | **35 / 91** | **129/402** | **14 局** | 中官×41、士绅×29、财帛×15 |

破产占比 24% → 14%，钱不再是默认死法（新的头号死因是内援断绝，那是选择的结果）；
死法同时更分散了（乡绅反目 13 → 27 局）。**岁俸刻意只补一半缺口，所以收益是"减半"而不是"清零"** ——
这是设计目标，理由写在 §五.9。
首屏负载几乎没动：20 个 JS / **2,698,429 B**（+297 B）。

**读这些数字之前必须知道的取样口径**（本轮踩到的，别再踩）：
`simulate.ts` 用 `vi.spyOn(Math,'random')` 把全局随机数换成种子流，所以
**同一份构建、同一批种子**是完全可复现的；但代码里只要多一个 `Math.random()` 消费者
（本轮就是那条生平记录的 id），整条抽样路径就会重排。因此
· **跨轮次直接拿 12 局的数字对照是错的** —— 本文上面第十一轮/第十二轮初稿里那句
  "35→49 月、86→188 事件"就是取样噪声，同一改动在 100 局下是 32→35 月、122→129 事件；
· 要比就把改动做成同一份构建里的开关，`SIM_GAMES` 开到 100 以上再对照；
· 默认 12 局只负责跑**不变量**（不崩、无 NaN、死于归零先见过警告），不用来看分布。

**新回归**：`tests/unit/engine.stipend.test.ts`（7 例）——
岁俸表逐条与 `RANKS.level` 对齐、非官员为 0、跨年恰好发一笔、
不跨年恒等于零笔、98 两 +6 裁到 100、警告在 random=0.99 下必出、
重病在 random=0.99 下必不出（且在 0.1 下能出，证明上一句是概率挡的不是条件写错）、
已警告过的维度不会被重复警告。

### 第十一轮：第一次让机器替人玩游戏 —— 以及它当场逮到的"第 13 个月悬崖"

前面十轮的体检全是**静态**的：查键名、查值域、查 id、查 flag 有没有人读。
这一轮补上的是缺的那一半 —— **把整局真的跑完**。
`tests/unit/helpers/simulate.ts` 是一个带种子的整局驱动器：
mulberry32 种子随机、`@testing-library/react` 的 `act` + `vi.advanceTimersByTimeAsync` 推时钟，
一局最多 260 个月，跑完输出局长/结局/事件触达集/八维终值/声明增量与实测增量对照。

**先说踩到的第一个坑，因为它决定了这份数据可不可信。**
第一版模拟器点完选项就接着点，于是同一个事件被连点 8–10 次，
出现过 `isGameOver === true 但没有 endingId` 的"假闪退"。
原因在引擎的推进模型：**`handleChoice` 从不清 `currentEvent`**，
真正的"翻篇"是玩家点「继 续」（`useGameEngine.ts:1459` 的 `handleContinue`，
先弹 `pendingEvents`，队列空了才 `handleNextMonth`）。
所以模拟必须走 选项 → 继续 → （无事件时）推进月份 这条**和 UI 一模一样的路径**；
`GameScreen.handleAdvance`（:186-193）与 `EventDisplay`（:421-430）就是这条路径的两个入口。
顺带把 `EventDisplay.checkChoiceRequirement` 导出来给模拟器复用 ——
判"这个选项锁没锁"必须用玩家自己那套规则，不能在测试里另写一份，
否则模拟的是另一个游戏。修好之后，`warden`（保命优先）策略再没出现过无结局的收尾。

#### 实测到的缺陷：守成玩法死在第 13 个月，死因是早就埋好的雷

修复前的数字（`SIM_POLICIES=steady`，随机避开"能直接收尾"的选项）：
**4 局里 3 局死在第 13 个月**（另 1 局 14），局长 min=13 max=14 avg=13，
一整局只碰得到 **31/402** 个事件、1~2 个结局，死因**全是中官归零 →「宦官构陷」**。
只有改成 max-min 的 `warden` 才能走到 1640–1644（触达 219/402）。

归因链条是三段，缺一段都会把结论下错：
1. `declaredDelta == actualDelta`（八维逐维对照）—— 引擎里**没有**暗扣，扣的就是选项声明的；
2. 出身初始 中官 只有 15~40（`src/data/origins.ts`），而全游戏**没有任何**中官的自然回复；
3. `THRESHOLD_ENDING_GRACE_TURNS = 12` 把宽限期内的归零变成**无声的**：
   不判死、也不告诉你已经归零。于是玩家在 0 值上又走了十几个月，
   `turn` 一到 12，那颗第一个月就埋下的雷当场引爆。

也就是说玩家视角看到的现象是"我啥也没干，第 13 个月突然死了"，
而代码里每个部件单独看都合理。这类缺陷静态审计是查不出来的 —— 它不是坏，它是**没有反馈**。

#### 修法：同一个维度，归零两次才要命

新增 `src/data/zeroWarningEvents.ts`：八条判死维度各配一条**手写**的 crisis 事件
（`boundary_warn_财帛/体质/圣眷/中官/清议/士绅/民望/道德值`，
标题囊橐萧然 / 病体支离 / 天颜不怿 / 内援已断 / 物议沸腾 / 乡里怨望 / 口碑大坏 / 本心蒙尘），
每条 3 个选项、各带完整 narrative 与 result 回音；三条口径统一的形状：
一条"用别的东西换这一维"、一条"花钱"、一条"少拿一点但代价最小"，没有一条是白拿。

规则改动落在判死线上：八条 `check` 从 `pastGrace(params) && <归零>` 改成
`doomedBy(params, key)` = **宽限期已过 且 归零 且 这一维已被警告过**。
事件效果统一由 `buildZeroWarningEvents()` 注入 `归零警告·X` flag（含"硬扛"那条 ——
警告的意义是"知道"，不是"必须救回来"）。维度名用 `ZeroKey` 字面量联合 +
`THRESHOLD_ENDING_BY_KEY` 表钉住：写成"清意"这类错字时 `src[key]` 取到 undefined，
判据恒 false，结局会静默消失 —— 正是第九轮在事件数据里查的那类毛病，
现在轮到边界规则自己，所以用类型钉而不是脚本钉。

为什么复用 `type:'crisis'` 而不新造机制：`checkBoundary`（引擎 :1317-1366）与挂载 effect
两边都已经接好了 `checkByType(params,'crisis')`，加类型只是多分一支求值器。

#### 修复后同一份模拟的实测

12 局 steady：局长 **min=15 max=62 avg=35**（原来 13），
触达事件 **86/402**（原来 31），触达结局 4 个，
**触达归零警告 6/8**（中官、圣眷、士绅、民望、清议、财帛），
结局分布 倾家荡产×6、宦官构陷×4、乡绅反目×1、民怨沸腾×1，
终局归零维度 财帛×6、中官×4、士绅×1、圣眷×1、民望×1，无"结局 id 未注册"的收尾。
`warden` 混跑仍然能推到 1644 甲申国变（触达 248/402）。

> **这批数字的取样口径**：都是 12~4 局的样本，而模拟器对 `Math.random()` 消费者数量敏感
> （见 §三 第十二轮末尾那条）。所以**可信的是结构性结论** ——
> "守成玩法集中死在第 13 个月""归零无声"这两条由 `pastGrace` 的定义直接决定，不靠取样；
> 而"31 → 86 事件""13 → 35 月"这类分布对照只能算方向感，别当测量值引用。

新增两条**长期钉住的不变量**（`tests/unit/simulation.playthrough.test.ts`，12 局一次跑完）：
- 无异常、无 NaN、每局都落到已注册结局；
- **死于某维归零 ⇒ 该维的 `归零警告·X` 必须在 flag 里**，
  同时要求 12 局里警告事件确实触达过（防止"永不触发"被当成"永不出错"）。

顺带把警告事件本身在 round-6 那份回归里逐维钉了一遍：
它是 `crisis`、至少 2 个选项、每个选项都写 flag、
"未警告过才出现"与"警告过才判死"两侧都要断言，
并且明确要求**别的维度的警告不作数**（中官警告过 ≠ 财帛归零可以判死）。

#### `npm run audit:economy`：归零维度的回升渠道体检

### 第十轮：两个主线事件被同一个 id 压住了 —— 外加第一次线上实测

`npm run audit:values` 上线之后，顺着它的 `eventsById` 往回数了一层，发现 `allEvents` 里
442 个对象只有 400 个不同 id。其中 40 个是**同一个对象被两个池子各引一次**
（情感线同时挂在 `initialEvents` 与 `emotionEvents`），无害；剩下 2 个是真正的撞号：

| 撞的 id | 撞在一起的两个事件 | 谁能播 | 谁被压住 |
| --- | --- | --- | --- |
| `historical_014` | 洪承畴降清（1639.ts）/ 孙传庭殉国（1643.ts） | 洪承畴降清 | **孙传庭殉国** |
| `transition_163` | 松锦战报与辽东密议（1641.ts）/ 新年朝会（1642.ts） | 松锦战报 | **新年朝会** |

失效链路是两条，叠在一起才致命：

1. `useGameEngine.ts:910` 的 `results.filter((e, i, arr) => arr.findIndex(x => x.id === e.id) === i)`
   把后出现的同 id 候选**直接从池子里删掉**；
2. `eventConditions.ts:175` 的 `new Set(eventHistory)` 按 id 判「播过了没」，
   于是播过一个之后，另一个在**同一局里**也永久出不来。

哪个能活纯粹取决于数组顺序（这里是年份文件正序，所以 1643 那场潼关之败、1642 那场新年朝会
从来没出现过）。这类 bug 的形态是「数据两头都写对了、单看哪个文件都不像坏的」，
只有把两份文件并起来数 id 才看得见 —— 所以 `transition_163` 的成因很直白：
1641 有 13 场（151–163），1642 又从 163 起头编，全局编号在年界上错位一格。

修法只改 id，不动内容：`historical_1643_sunchuanting` / `transition_1642_newyear`
（沿用数据里既有的 `<池>_<年>_<语义>` 命名，如 `transition_1643_*`、`historical_024_aftermath`）。
**存档不受影响**：旧档 `eventHistory` 里那个 `historical_014` 本来就只可能是洪承畴降清
（被压住的那场压根没播过），保留原 id 的正是它 —— 所以既不用迁移也不用动 `SAVE_SCHEMA_VERSION`，
而新 id 对旧档是全新的，恰好让这两场第一次真的能播。

顺带两笔：
- `audit-value-domains.ts` 增加撞号规则（DEAD 类）。判据是**内容**而不是引用：
  标题 + 选项 id 序列相同视为同一条内容的重复导出，不报；不同才报。
  只比引用的话，以后池子改成 `list.map(e => ({ ...e }))` 就会一口气造出 40 条噪音，
  而噪音的下场永远是被后人加豁免。
- 第九轮那份 `scanValueDomains` 里的 `seen` map 建完就没读过，本轮把它改成撞号检查本身。

### 第九轮：类型管得住键名，管不住值 —— 以及一批「有声明、无实现」的假接口

第八轮把 `@ts-nocheck` 清零、键名收紧之后，数据侧还剩一整个维度是 tsc 看不见的：
`conditions.origin` / `conditions.rank` / `storyline` / `linksToEndingId` 这些声明就是 `string`，
tsc 只保证「它是个字符串」。而引擎拿它们做的是集合判断 ——
出身写成「晋绅」（正字「缙绅」）编译通过，运行时 `allowed.includes(character.origin)` 恒 false，
事件在任何存档里都选不中。失效方向和第七轮那批死事件一模一样，只是错的位置从键名挪到了值。

**新建 `scripts/audit-value-domains.ts`（`npm run audit:values`）**，拿运行时真值当词表对账：
出身表 4 项、`RANKS` 官阶 18 级、`STORYLINES` 15 条、结局池 43 个、开局年 `GAME_START_YEAR`，
外加 `public/` 的目录实况。查六类：值不在词表（DEAD）、区间倒置 / 月份越出 1..12 /
年份窗口早于开局年（DEAD）、边界宽到等效于没写（NOOP）、剧情线拼错（NOOP）、
prelude↔ending 悬空或单向（LINK）、数据里的站内资源路径查不到文件（LINK）。
结论：**400 个事件，DEAD 0 / NOOP 0 / LINK 0** —— 数据现在是干净的，
但本轮真正的产出是「以后能一直干净」：`tests/unit/valueDomains.silentFailures.test.ts` 12 例，
一半钉真实数据为 0，一半用人造坏事件钉「每一类错误都真抓得住」，
再钉住词表规模本身（词表哪天被 import 成空集合，体检会绿得毫无意义）。

真正动手修的是三批静默死内容：

| 缺陷 | 规模 | 处理 |
| --- | --- | --- |
| `showConditions: { custom: () => !0 }` —— 选项级条件里挂着一个**恒真的 lambda** | `endings_all.ts` 37 处 | 双死：`EventDisplay.checkChoiceRequirement` 走的是 attributes/gameState/hidden/flags/出身/体质六条判定，**根本不调用 custom**；就算调用，`() => !0` 也永远为真。整个块删除（行为等价：`showConditions` 缺省与"只有 custom"都是 `available: true`）。这批东西的来历是 `endings_all.ts` 由 `dist` 压缩包还原，`!0` 是压缩器留下的 `true` |
| `narrative.speaker.avatar` 指向 `/avatars/*.png` | 40 个文件 301 处 | `public/avatars/` 这个目录**从来不存在**（dist 里也没有），且没有任何组件读这个字段 —— 话者头像一直是按姓名首字现画的 SVG 印记。字段与 301 处一起删；值域体检新增资源路径存在性检查，专门拦这一类「接进 UI 就是 301 张碎图」的假接口 |

删 `nextEvents` 的时候顺手拆掉两句**假文档**（`utils/eventConditions.ts` 的 `pickEvent` 头注释）：
「如果上一事件的 `nextEvents` 列表里有当前可用事件，则 100% 命中第一个匹配项」—— 那段实现从来没有，
数据里也没有一处写过 `nextEvents`；「同 key 前缀 storyline 加权 2 倍（兼容子线）」—— `pickEvent` 里那行
`return 1` 上面挂着这句话，真正的前缀加权在 `useGameEngine.weightedPick`（`startsWith` → 3 倍）。
假注释比没注释更贵：下一个人会照着它写数据，然后发现自己的链是断的。

`preludeEventId` ↔ `linksToEndingId` 这一对**保留**，但把话说清楚：运行时决定"前奏强制优先播放"的
是事件上的 `isPreEnding`，这两个 id 字段没人读，它们的全部意义是"人和人之间的双向指认"。
所以配对完整性改由体检脚本钉（悬空 = LINK，对面没回指 = LINK，有链接却缺 `isPreEnding` = NOOP），
`valueDomains` 测试另加一条：现存的 5 对必须**双向齐全且都带 `isPreEnding`**。

`GAME_START_YEAR = 1628` 从 `useGameEngine` 里导出。此前 `1628` 在引擎散写 5 遍
（三处初始 gameState + 一处生平小结 + 一处存档守卫），改一局开局年份要同时改五个地方；
值域体检也需要它才能判断「`year.max` 早于开局年 = 时钟只往前走，永远等不到」。

顺带把两个体检脚本共用的池子清单抽成 `scripts/event-pools.ts`。以前"有哪些池子"在两个脚本里各抄一遍，
新加一个池子只改一处，另一处就会**静默少查一批事件**，而"少查一批"在报告里长得和"全部干净"一模一样。
单独成文件的另一个原因是每个体检脚本末尾都挂着 CLI 输出块，互相 import 会顺带打印别人的报告。

结果：**400 事件 / 43 结局，`audit:shape` 与 `audit:values` 双双 0 处**，六个体检脚本全绿，
`tsc` 与 `tsc -p tsconfig.test.json` 双 0 错，176 例通过，`vite build` 通过，桌面端 smoke 通过。

方法论两条。**其一**：删字段必须留探针。上一轮删 `EndingConfig.unlocksAchievement` 时没留，
于是"它被删过"这件事唯一的证据是 git log。这轮在 `types.keysMatchEngine.test.ts` 补了 11 枚
`@ts-expect-error`，谁把字段加回来 `typecheck:test` 立刻红 —— 顺带踩到一个 tsc 行为：
**一个对象字面量只报第一个未知键**，所以一枚探针只能钉一个字段，那些钉子得拆成 11 个字面量才数得清。
**其二**：值域和键名是两半，类型系统只管得到一半；另一半要么靠 `as const` 枚举逼进类型里
（`origin` 以后若变成 `keyof typeof origins` 就好了这一半），要么就靠脚本 —— 现在选了脚本，
因为词表本身住在数据里，类型反向依赖数据会让 `types/` 变成循环。

### 第八轮：拆掉盲区本身，以及 BOM 让"清零"变成假阴性

第七轮的收尾是"要么哪天真的给数据补上类型，要么就一直养着这个体检脚本"。
这一轮选了前者：`src/` 里的 `@ts-nocheck` **一个不剩**，400 个事件、上万条数值第一次整体回到类型系统。

**但先要说的是自己踩的坑。** 第七轮末尾我用 `grep -rl '^// @ts-nocheck' src` 得到 0 个文件，

（`eventShape.silentFailures.test.ts` 的「类型检查盲区不得重新出现」：`src/` 里既不许有
`@ts-nocheck`，也不许有 BOM 开头的文件）。

第六轮末尾我写了一个结构体检脚本手工跑，一跑就掉出两类真缺陷。

## 四、测试基座本身踩到的坑

记录在 `tests/unit/README.md`，这里只列要点：

1. **Node 26 内置的实验性 `localStorage` 会覆盖 jsdom 的实现**。现象极具迷惑性：
   jsdom 明明加载成功（`window` / `document` / navigator 都正常，UA 也是 `jsdom/30.x`），
   但 `localStorage` 是 `undefined`，引擎一读存档就抛
   `Cannot read properties of undefined (reading 'getItem')`。
   已在 `setup.ts` 装符合 Storage 规范的内存实现（含 `length` 与 `key(i)`）。
2. **`Math.random` 必须固定**，否则事件挑选、掷骰、临界事件判定都会让用例随机失败。
3. **等待时间要覆盖引擎的调度定时器**。`handleNextMonth` 只在 300ms 的 `setTimeout`
   里才挑事件、写历史；`advanceMonths` 早先只等 30ms，导致针对"事件历史是否重复"
   的断言其实什么都没测到。
4. **`vi.runAllTimers()` 只跑一轮是不够的**。投骰的第二级定时器是在 `setState`
   更新函数里排的，而 React 要等 act 这一轮结束才执行更新函数 ——
   只跑一轮时第二级定时器还没排上，用例会**空过**。必须
   「跑定时器 → 让 React flush → 再跑」交替若干轮。

## 五、刻意保留的设定（不是遗漏，请勿"顺手修掉"）

### 1. 调试面板「幽灵模式」的默认值由构建模式决定

**现状**：`src/utils/debug.ts` 的兜底返回值不再是硬编码 `true`，
而是构建期注入的常量 `__DEBUG_PANEL_DEFAULT__`（`vite.config.js` 里 define）：

| 构建命令 | 用在哪 | 默认 |
| --- | --- | --- |
| `npm run build` | GitHub Pages 演示站、本地 preview | **开启** |
| `npm run build:steam` | Electron / Steam 发行物（`desktop:dist` 会自动先跑它） | **关闭** |

**为什么这么设计**：这个面板能改属性、跳年份，并直接浏览**全部事件与全部结局**
（含未解锁结局），对玩家是彻底剧透 —— 商业发行不允许默认暴露。
但它同时是项目所有者本人的开发/试玩工具，演示站上确实需要。

如果只用"改源码里那行 `return true`"的做法，会有两个真实风险：
忘了改回来就发行了剧透面板；或者反复切换时改错了方向。
**按构建模式区分**让两边都不需要改代码 —— 一条命令决定，且可被 CI 验证。

**逃生口**：`?debug=0` 隐藏（会记住），`?debug=1` 恢复，任何构建都有效。

**回归保护**：CI 会实跑一次 `npm run build:steam`；
`tests/unit/debugSwitch.test.ts` 钉住 `?debug=` 与 localStorage 的优先级。

### 2. `pickEvent` 里"最近 5 条"不能用 `seen` 集合替代

**现状**：判定支线事件"最近是否出现过"时用的是 `eventHistory.slice(-5)`，
而不是全部已触发历史。

**原因**：支线事件（情感线 / 权色线）**设计上就是可重复的** —— 玩家会反复遇到
同一段关系或同一桩买卖。若改成"排除全部已见"，支线会被永久耗尽。
本轮改造 `pickEvent` 性能时踩过这个坑，是 `noUnusedLocals` 报错
（`recent` 变量不再被使用）才暴露出来的。

**不要"顺手优化"掉那两处 `new Set(eventHistory.slice(-5))`。**

### 3. 阈值结局的两道闸门：12 个月宽限期 + 必须先见过警告

**现状**（第十一轮改过，别再往回改）：`src/data/boundaryEvents.ts` 里 8 个"数值归零即达成"的结局
（破产 / 病故 / 圣眷尽失 / 中官构陷 / 清议不容 / 士绅反叛 / 民变 / 道德沦丧），
判定统一走 `doomedBy(params, key)`，展开是**两个条件与**：
`pastGrace(params)`（`gameState.turn >= 12`）**且** `isFatalZero(params, key)`（这一维归零 且 flag 里有 `归零警告·X`）。

**为什么要有宽限期**：这条判定本身没问题，问题在于它在**开局第一个月**就会误杀。
寒门出身 `财帛 = 15`，而开局事件「家书催银」的第一个选项扣 20 两 ——
15 − 20 = 0，`bankrupt` 当场达成。玩家刚点下第一个选项就看见
「【结局】倾家荡产」，整局在 turn=1 结束。
挂载路径（读档进来）同样会立刻重播。
这类"阈值结局"的语义是**长期状态恶化到无法挽回**，不是"单个月份的瞬时读数"，
所以给一年宽限期是符合设计的。

**为什么宽限期还不够**：整局模拟器实测到，只加宽限期等于把归零变成**无声的雷** ——
宽限期内归零不判死、也不告诉玩家，于是守成玩法在 0 值上白走十几个月，
`turn` 一到 12 当场炸死（实测 3/4 局恰好死在第 13 个月，死因全是中官）。
所以第二道闸门是**先给活路、再讲后果**：第一次归零弹一条专属危机事件（见 `zeroWarningEvents.ts`），
玩家救回来了就继续玩；救不回来、再次归零，结局才收尾。
合起来一句话：**同一个维度，归零两次才要命**。

**刻意没有加宽限期的两条**：`serious_illness`（体质 1–19）是 `crisis` 而非 `ending`，
它是"重病缠身、需要立刻抉择"的玩法事件，本来就该随时出现。

**回归保护**：`engine.regressionRound6.test.ts` §八 钉住了"turn < 12 不成立"，
以及两侧新规则 —— "期满归零但没警告过 ⇒ 不判死"、"警告过之后再次归零 ⇒ 判死"，
外加逐维的"未警告才出警告 / 已警告才出结局"，并明确要求**别的维度的警告不作数**。
`simulation.playthrough.test.ts` 再从整局层面钉"死于归零 ⇒ 先见过警告"。

### 4. 结局分支之前必须先 `setGameState`

`useGameEngine.ts` 的 `handleChoice` 里，五方态度的 `setGameState`
排在 `special.type === 'ending'` 分支**之前**。这不是随手挪的：
结局屏和史馆传略都会读 `gameState`，若让结局分支先 return，
玩家看到的局势就是"属性改了、态度没改"的半成品。
`regressionRound6.test.ts` 用 `清议 +10` 的辞官选项钉住了这一点 ——
改之前拿到的是原值 50，改之后是 60。

### 5. 存档 schema 已到 v4，`currentEvent` 也走兜底

`SAVE_SCHEMA_VERSION = 4`：v4 新增 `meritBonus`，并把 `currentEvent` /
`pendingEvents` 纳入 `migrateSave` 的规整范围（`normalizeEvent`）。
**这条属于项目既有信条的延伸：兜底必须发生在数据层，不能指望每个组件自己判空。**
组件是直接用下标访问 `currentEvent.choices[i].text` 的，
一个被外部改坏的存档就能让它在渲染第一帧撞进 ErrorBoundary。

### 6. `manualChunks` 的年份分桶是刻意的粗粒度

`vite.config.js` 的 `historicalBucket`（4 年一片）与 `transitionBucket`（5 年一片）
取代了原先的"一年一片"。不要改回逐片 —— 那 46 个分片不会因为拆得更细而变少，
`events/index.ts` 是静态 import，首屏照样全量预取，多出来的只是 23 次请求往返。

### 7. 体检脚本剩下的噪音，是刻意不清理的

原先列在这里的第一条 —— 11 处 `result.echo_2: ''`（`echo` 装的是完整回声文本，
`echo_2` 是当初想写两段式回声留下的空键）—— 第八轮摘 `@ts-nocheck` 时它是 TS2561，
顺手删干净了。现在 `npm run audit:shape` 报 **0 处**结构告警，
`eventShape.silentFailures.test.ts` 里那条断言也从"只允许是 echo_2、且不超过 11 处"
收紧成 `toEqual([])`：**再没有"已知噪音"可以往里藏东西**。

另两类同源噪音不打算"顺手修掉"：216 个只写不读的 flag（见第一节 1.1），
以及引擎对未知键的宽容姿态 —— `conditions.gameState` 撞上不认识的键时，
比较的是 `undefined`，两侧都为 false，于是**静默跳过这条条件**而不是否决整个事件。
把它改成"未知键即否决"确实更符合"宁可少触发也别错触发"，但代价是
旧存档配新数据、或新数据配旧引擎时，一批事件会集体消失，而消失比提前触发更难被发现。
所以这里的取舍是：**引擎保持宽容，用 CI 里的体检脚本把错键名挡在数据层**
（与本仓库"兜底发生在数据层"的信条一致，见第五节第 5 条）。

第三处"看着像 bug、其实是有意的不一致"值得单独记一笔：未知键在三个位置的兜底值各不相同
—— 池判定的属性走 `attributes[key] \|\| 0`，池判定的状态撞上不认识的键是"跳过"，
而选项门 `EventDisplay.checkChoiceRequirement` 对属性和状态一律 `?? 50`。
`?? 50` 这一档最危险：打错的键名会**碰巧通过所有 ≤50 的要求**，
既不报错也不消失，只是把门槛悄悄放宽了。类型收紧之后这类键名已经写不出来，
所以引擎不改；但要动它，先读这段。

### 8. 数据里零用法、但引擎实现齐备的字段，是留着的（第九轮已核对，请勿当死代码删）

第九轮逐字段对过一遍「数据写了几处 / 代码谁读了」，下面这几个是**反过来的那种**：
实现完整、一处数据都没有。

- `EventChoice.staminaCost / staminaRequired / staminaBonus` —— 体力的消耗、门槛与回复。
  `checkChoiceRequirement` 会据此把选项锁成"体质不足"，`useGameEngine` 会真的加减 `体质`。
- `EventChoice.failEffects / failResult / failResultDescription` —— 投骰失败分支的作者自定义写法。
  没写时引擎用 `deriveFailEffects(choice)` 兜底，所以这条路径天天在跑，只是没人覆盖默认值。
- `EventEffects.meritScore` —— 选项显式政绩分。引擎计入 `meritBonus` 并参与升迁（第六轮修过它的落账 bug），
  数据侧目前全部走"由属性推导"这条路。

判据不是"有没有数据用过"，而是"删掉它会不会让一段**能跑的代码**失去入口"。
这三组都会：删了就是把功能拆了。真要清理，正确方向是给它们补数据（或把引擎分支一起删），
而不是只删类型声明。反过来，第九轮删掉的那 11 个字段（`nextEvents` / `DiceCheck` /
`charactersAlive` 之类）是**代码里一个读取点都没有**的那种 —— 两边的区别就在这一点上。

### 9. 岁俸的量级是刻意压着的，不要"顺手调高"（第十二轮）

**现状**：`annualStipend(rankName)` = 该级 `RANKS.level` 两/年，只在跨年时发，
受 `ATTR_BOUNDS.财帛` 的 0..100 裁剪。七品官一年 6 两，约等于把实测到的
−0.77/月出血补掉一半多一点。

**为什么是这个数**：`财帛` 上限只有 100。月薪开到 2 两以上，正常玩法就会长期顶格，
「倾家荡产」以及挂在破产线上的那批结局**再也触发不了** —— 那不是修平衡，是把一整族内容删了。
现在的目标函数是"省着花能活、随便花照样破产"，判定标准写在
`simulation.playthrough.test.ts` 打印的结局分布上：**倾家荡产应当还在，但不再是多数**。
第十二轮之后是 2/12（改之前 8/16）。

**如果以后要改**：调之前先跑一遍模拟器拿到改动前后的分布对照，别凭手感改数字 ——
这一条之所以能被写出来，就是因为上一轮先有了量尺。同理，别给中官也加一条被动回复：
关系不会自己回暖，要加得加成一条有代价的玩法（见 §1.4 ②）。

### 10. 图鉴点亮刻意允许"没有成就也算达成"（第十三轮）

**现状**：`AchievementData.reachedEndings`（格子 id → 首次达成时间）与成就表是**两条独立的链**。
`triggerEndingAchievements` 先无条件写这条记录，再去解 `${event.id}_done` ——
后者在成就表里查无此 id 时是个静默 no-op（`unlockAchievement` 守的就是这个）。
于是 10 条 `triggerable_*` 边界结局和"罢黜归田"这一格，**玩家在本机图鉴里看得见，
Steam 侧却没有对应成就**（名额被 `STEAM_ACHIEVEMENT_LIMIT = 100` 用满，见 §1.4 ⑥⑦）。

**为什么不是 bug 而是取舍**：把"打过"记下来不需要任何人批准，加一条成就需要。
如果坚持"图鉴只反映成就"，那 11 格会永远灰着 —— 玩家明明打出来了，界面说他没有。
**别把它"顺手统一"回去**，也别反过来偷偷往成就表里塞东西：`endingCodex.registry.test.ts`
有一条用例专门钉"没有成就的格子被达成之后，成就表里不会凭空多出一条"。

**要动它就先动名额**：`RETIRED_ACHIEVEMENT_IDS` 这条路是通的（退役 id 在
`cloneAchievementData` 里被过滤掉，老存档也不会因此报错），
想给某条边界结局补成就，先从那里退役等量的低价值条目，再把
`scripts/audit-ending-codex.ts` 的 `KNOWN_TILES_WITHOUT_ACHIEVEMENT` 里那条名字划掉 ——
划不干净体检就会红（它同时是下限和上限）。
